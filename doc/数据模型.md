# ODMatrix 数据模型

## 1. 目标

本文档定义采集端的核心数据对象、网格化规则与 JSON 导出格式，作为后续实现与前后端联调的统一契约。

## 2. 基本术语

- **Origin**：出发位置
- **Destination**：目的地位置
- **Purpose**：出行目的
- **Grid ID**：离散化后的网格编号，格式为 `GridX_GridZ`
- **Grid Index**：在固定网格遍历顺序下分配的唯一整数索引
- **OD Event**：一次原始出行需求事件
- **Compact OD Record**：正式运行模式下的压缩路径记录
- **Snapshot**：某个时间窗口内的聚合导出结果
- **PrimaryIntent**：在去重窗口内被认定为真实出行意图的首个事件
- **Retry**：在去重窗口内被判定为同一意图的重复触发事件
- **Compare Probe**：用于对照的路径层埋点事件，不作为主 OD 统计口径
- **CapturedAtUtc**：事件被 Mod 记录时的现实世界 UTC 时间
- **GameTime**：事件发生时对应的游戏内绝对时间
- **NormalizedTimeOfDay**：游戏内单日进度，通常归一化到 `0..1`

## 3. 网格规则

### 3.1 网格尺寸

默认网格边长为 `20u`。

PRD 中也给出了“约 160 米 × 160 米”的语义说明，但在代码实现中应以游戏坐标单位为准，并通过统一函数进行换算。

### 3.2 坐标转网格

推荐统一规则：

- `gridX = Floor(worldX / gridSize)`
- `gridZ = Floor(worldZ / gridSize)`
- `gridId = gridX + "_" + gridZ`

### 3.3 网格顺序索引

正式运行模式下，应基于固定的网格遍历顺序为每个网格生成唯一整数索引。

要求：

- 遍历顺序必须稳定且可复现
- 同一地图配置下，索引生成结果必须一致
- 压缩记录内部优先使用整数索引，而不是字符串网格 ID

推荐约束：

- 以固定 `gridX -> gridZ` 或 `gridZ -> gridX` 顺序遍历
- 在文档和代码中统一，只允许一种顺序
- 导出时如需可读性，可再反解为 `GridX_GridZ`

### 3.4 边界处理

需要明确以下情况的实现策略：

- 负坐标如何处理
- 地图边界外或非法坐标如何跳过
- 水面、地图外、无效路径点是否记入统计

建议初版策略：

- 非法坐标直接丢弃
- 记录丢弃计数到诊断日志

## 4. 出行目的枚举建议

为降低初期复杂度，建议先使用有限枚举：

- `Unknown`
- `Work`
- `School`
- `Shopping`
- `Leisure`
- `Service`

导出到 JSON 时建议统一转为小写字符串键：

- `unknown`
- `work`
- `school`
- `shopping`
- `leisure`
- `service`

## 5. 运行时对象建议

## 5.1 原始事件对象

建议字段：

- `DateTime CapturedAtUtc`
- `DateTime GameTime`
- `float? GameHour`
- `float? NormalizedTimeOfDay`
- `string Purpose`
- `float OriginX`
- `float OriginZ`
- `float DestinationX`
- `float DestinationZ`
- `string SourceTag`（可选，用于记录来源补丁点）

该对象主要用于：

- 调试模式下忠实保留原始记录
- 人工抽样稽核数据正确性
- 为压缩记录生成提供输入

建议新增字段：

- `TravelerType`：`Resident` / `Tourist`
- `SignalType`：`PrimaryIntent` / `Retry`
- `DeduplicationKey`：时间窗口去重键
- `DuplicateCountInWindow`：当前窗口内重复次数

时间字段约定：

- `CapturedAtUtc` 用于日志对账、跨会话排序与外部文件时间统一
- `GameTime` 用于后续 OD 分时段分析，是正式数据模型的一部分
- `GameHour` 可选，用于快速按小时分桶
- `NormalizedTimeOfDay` 可选，用于昼夜节律、跨天归一化分析

当前依赖反射已确认以下游戏内时间候选 API 可用：

- `SimulationManager.m_currentGameTime : System.DateTime`
- `SimulationManager.m_currentDayTimeHour : System.Single`
- `SimulationManager.m_dayTimeFrame : System.UInt32`
- `SimulationManager.FrameToTime(uint frame) : System.DateTime`
- `DayNightProperties.normalizedTimeOfDay : System.Single`

建议优先口径：

- 第一优先：记录 `SimulationManager.m_currentGameTime`
- 第二优先：补充 `m_currentDayTimeHour`
- 第三优先：如需统一昼夜分析，再补充 `normalizedTimeOfDay`

设计原则：

- 事件对象尽量轻量
- 不要嵌入复杂引用对象
- 不要长期保留游戏对象引用，避免生命周期问题

## 5.2 聚合键

建议聚合维度：

- 出行目的
- 方向（outbound / inbound）
- 主网格
- 关联网格

并增加以下口径约束：

- 主聚合默认只消费 `PrimaryIntent`
- `Retry` 默认只进入诊断统计
- `Compare Probe` 单独统计，不直接进入 OD 主矩阵

## 5.3 压缩路径记录

正式运行模式下，建议使用压缩记录对象替代完整原始事件参与后续处理。

推荐字段：

- `int OriginIndex`
- `int DestinationIndex`
- `int Payload`
- `int TimeSlice`（可选）

其中 `Payload` 可根据实现阶段承载：

- 出行目的枚举值
- 计数占位
- 时间分片或其他紧凑信息

如果后续需要按游戏内时段导出或聚合，推荐把 `TimeSlice` 设计为独立整数字段，而不是与 `Payload` 强耦合，便于保持目的字段与时间字段的可解释性。

这意味着在最追求性能的情况下，一条路径可仅由三个整数描述。

## 5.4 双模型策略

建议代码层面明确区分：

- 调试模式：保留 `ODEvent`
- 正式模式：优先使用 `CompactODRecord`

两者不应混为单一超大对象，以免让调试字段拖累正式运行性能。

## 6. 内存聚合结构

推荐逻辑结构如下：

```text
Purpose
└─ Direction
   └─ PrimaryGridId
      └─ RelatedGridId -> Count
```

示例：

```text
work
└─ outbound
   └─ 102_45
      ├─ 105_50 -> 120
      └─ 200_12 -> 45
```

为了便于查询，建议同时维护两套索引：

- outbound：从某源网格出发，去往哪些目的网格
- inbound：到达某目标网格，分别来自哪些源网格

补充建议：

- 调试模式可额外保留原始记录集合或抽样记录集合
- 正式模式只保留聚合结果，不保留完整原始事件流水
- 游客与居民可共用同一事件模型，但应保留明确类型字段

## 7. JSON 快照格式

建议导出格式：

```json
{
  "meta": {
    "version": "1.0",
    "gridSize": 20,
    "snapshotTime": "2026-05-26T21:30:00",
    "gameTime": "2024-03-15T08:30:00",
    "normalizedTimeOfDay": 0.354,
    "saveName": "MyCity",
    "eventCount": 123456
  },
  "matrices": {
    "work": {
      "outbound": {
        "102_45": {
          "105_50": 120,
          "200_12": 45
        }
      },
      "inbound": {
        "105_50": {
          "102_45": 120
        }
      }
    }
  }
}
```

## 8. 字段约定

### 8.1 meta

- `version`：导出格式版本，而不是程序集版本
- `gridSize`：网格边长
- `snapshotTime`：快照生成时间，建议 ISO 风格字符串
- `gameTime`：快照生成时对应的游戏内时间，建议 ISO 风格字符串
- `normalizedTimeOfDay`：快照生成时的日内归一化进度，可选
- `saveName`：城市存档名，可选
- `eventCount`：本次快照累计事件数，可选

### 8.2 matrices

- 第一层键：出行目的
- 第二层键：方向 `outbound` / `inbound`
- 第三层键：主网格 ID
- 第四层键：关联网格 ID
- 最终值：出现次数

## 9. 版本策略

建议从 `1.0` 开始，并在以下场景升级格式版本：

- 修改 JSON 顶层结构
- 修改关键字段命名
- 调整网格 ID 规则
- 引入新的必填元数据

如果只是新增可选字段，可保持次级兼容，不必立刻变更大版本。

## 10. 初版实现建议

初版优先保证：

- 字段少而稳定
- 易于序列化
- 前端容易解析
- 输出体积可控

同时建议区分两类输出：

- 调试输出：允许包含原始记录或抽样记录，用于人工核对
- 正式输出：以聚合矩阵为主，不输出完整原始流水

初版暂不建议：

- 输出复杂对象数组
- 在 JSON 中冗余重复地图元信息

补充说明：

- “不建议输出每条原始事件”适用于正式模式
- 调试模式可在显式开关开启时导出原始记录或抽样记录

## 11. 校验清单

实现时应验证以下内容：

- 同一事件是否正确同时写入 outbound / inbound
- 网格换算是否在边界值上稳定
- JSON 在空矩阵、单节点、多节点场景下均可正确输出
- 非法目的类型是否统一归类为 `unknown`
- 快照时间与事件总数是否准确
- 游戏内时间字段是否与同一时刻的实际游戏状态一致
- 调试模式下原始记录与聚合结果是否能相互对账
- 正式模式下整数索引是否可稳定反解为网格 ID
- 去重窗口内是否能稳定区分 `PrimaryIntent` 与 `Retry`
- 游客记录是否被单独识别并纳入总统计
- `PathManager.CreatePath` 对照计数是否可与意图层数量形成可解释差异
