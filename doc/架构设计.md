# ODMatrix 采集端架构设计

## 1. 文档目的

本文档描述 `ODMatrix` 游戏数据采集端的目标架构、模块边界、线程模型与实现约束，用于指导后续 Mod 开发。

当前仓库仍处于骨架阶段，本文内容以“推荐实现方案”为主，而不是既有代码说明。

## 2. 系统边界

本仓库只负责以下职责：

- 在 Cities: Skylines 1 运行时截获原始出行需求
- 将坐标降维为固定网格
- 在内存中进行稀疏聚合
- 将快照导出为 JSON 文件

本仓库不负责以下职责：

- 地图底图渲染
- Web 可视化界面
- Leaflet / Canvas 前端交互
- 交通策略分析与评分

整体数据流保持为：

`Game Runtime -> Harmony Patch -> Event Buffer -> Aggregator -> Snapshot Exporter -> JSON`

同时引入两种运行模式：

- `DebugAudit`：开发/调试模式，尽量忠实保留原始居民出行记录，便于人工稽核
- `ReleaseCompact`：正式运行模式，使用固定网格顺序索引压缩路径表示，优先追求性能与内存效率

## 3. 约束条件

### 3.1 技术约束

- 目标框架为 `.NET Framework 3.5`
- 项目类型为类库，由游戏运行时加载
- 依赖 Harmony 进行运行时补丁注入
- 使用本地 Cities: Skylines 安装目录中的 DLL 作为编译引用

### 3.2 设计约束

- 不得在高频游戏线程上执行重型序列化或磁盘 I/O
- 不得以建筑 ID 作为稳定输出主键，应统一输出网格 ID
- 输出应面向“离线分析”而非“实时联机同步”
- 应优先保证稳定性，再追求完整的出行目的识别
- 开发阶段需要支持可人工稽核的原始记录调试模式
- 正式运行阶段应允许切换为压缩整数索引表示
- 游戏内总日志只记录生命周期状态，详细日志写入本 Mod 独立文件
- 代码应优先组织在 `src/` 目录下，按职责分层
- 当前统计周期从 Mod 在本次会话启用后开始，不补算读档前已在途或已有目标的居民/游客
- 游客出行需要纳入采集范围
- 需要在意图层采集中加入去重机制，区分 `PrimaryIntent` 与 `Retry`
- 需要保留一个路径层对照埋点用于比较意图数量与寻路请求数量

### 3.3 兼容性约束

由于项目仍为 `.NET Framework 3.5`：

- 不使用 `Task`、`async/await`、`ConcurrentQueue<T>`
- 后台处理建议使用 `Thread`、`Monitor`、`lock`、`Queue<T>`
- 序列化方案应优先选择兼容 net35 的实现

## 4. 建议模块拆分

## 4.1 Bootstrap / Mod 入口

职责：

- 负责 Mod 名称、描述、用户可见信息
- 在启用时完成 Harmony 初始化
- 在停用或重载时安全卸载补丁与后台线程

建议产物：

- `LoadingExtension` 或等效入口类
- `ModInfo` / `IUserMod` 实现
- 生命周期协调器

## 4.2 Patch Layer

职责：

- 对候选游戏方法打补丁
- 从参数、上下文或调用栈中提取出发点、目的地与目的类型
- 将原始数据转换为内部事件对象

候选埋点：

- `ResidentAI.StartTransfer`
- `TouristAI.StartTransfer`
- `PathManager.CreatePath`
- 与 Citizen / Transfer / AI 决策直接相关的方法

说明：

`ResidentAI.StartTransfer` / `TouristAI.StartTransfer` 作为当前真实出行意图的主统计入口；`PathManager.CreatePath` 作为路径层对照埋点，用于评估重试和重复寻路。

## 4.3 Event Buffer

职责：

- 接收高频采集事件
- 降低补丁代码与聚合逻辑耦合
- 控制主线程停留时间

推荐实现：

- `Queue<ODEvent>`
- `object _syncRoot`
- 使用 `lock` 保护入队与批量出队

不建议：

- 在补丁方法中直接修改复杂嵌套字典
- 在补丁方法中直接写磁盘

补充说明：

- 调试模式下，缓冲区可先承接原始 `ODEvent`
- 正式模式下，缓冲区可优先承接压缩后的整数路径记录
- 两种模式都应共用统一的线程同步策略，避免维护两套并发模型
- 原始记录进入缓冲区前应先完成去重分类，明确是 `PrimaryIntent` 还是 `Retry`

## 4.4 Aggregator

职责：

- 将事件流按出行目的、源网格、目标网格累加
- 同时维护 outbound / inbound 两种方向索引
- 控制内存增长与快照边界

推荐内存结构：

- 第一层：出行目的，如 `work`、`school`、`shopping`、`leisure`
- 第二层：方向，如 `outbound`、`inbound`
- 第三层：主网格 ID
- 第四层：关联网格 ID -> 计数

建议将聚合器拆成两个入口：

- `RawRecordAggregator`：面向调试模式，消费完整原始记录并支持人工核对
- `CompactAggregator`：面向正式模式，消费压缩后的整数索引记录并做高效累加

补充约束：

- 后续 OD 聚合默认以 `PrimaryIntent` 为主统计口径
- `Retry` 事件保留为诊断与调参数据，不默认计入主结果

## 4.5 Grid Mapper

职责：

- 将世界坐标映射为固定网格 ID
- 统一坐标离散化逻辑
- 保证导出结果可复现

建议规则：

- 网格边长：`20u`
- 存储时使用文档约定换算结果
- 统一输出格式：`GridX_GridZ`

若后续确认游戏世界单位与外部 PRD 示例存在差异，应在一个地方集中调整，而不是散落在补丁与导出逻辑中。

进一步建议：

- 维护一个固定、可复现的网格遍历顺序
- 为每个网格分配稳定的顺序索引
- 在正式模式下使用顺序索引替代字符串网格 ID 参与中间处理
- 仅在导出或调试展示时再转换为可读网格 ID

## 4.6 Snapshot Exporter

职责：

- 将当前内存聚合结果生成快照对象
- 写入标准 JSON 文件
- 维护元数据（版本、时间、网格大小、地图信息）

建议输出目录：

`%LOCALAPPDATA%\Colossal Order\Cities_Skylines\ODMatrix\`

建议命名方式：

`odmatrix_{saveName}_{yyyyMMdd_HHmmss}.json`

## 4.7 Diagnostics

职责：

- 记录初始化状态
- 记录补丁是否成功应用
- 记录快照导出成功或失败
- 记录事件吞吐量与异常统计
- 记录主意图数量、重试数量、游客数量和路径层对照数量

日志分层建议：

- 游戏日志：仅写入启动、关闭、补丁加载、导出完成/失败等摘要状态
- 独立日志文件：写入调试记录、异常细节、人工稽核信息、模式切换信息

建议初期仅保留轻量日志，不要在高频路径中大量拼接字符串。

独立日志建议目录：

`%LOCALAPPDATA%\Colossal Order\Cities_Skylines\ODMatrix\Logs\`

## 4.8 Source Layout

建议从后续实现开始，代码统一按以下结构落入 `src/`：

- `src/Bootstrap/`：入口、生命周期、Harmony 初始化
- `src/Patches/`：补丁类
- `src/Models/`：原始记录、压缩记录、快照模型
- `src/Aggregation/`：缓冲区、网格索引、聚合器
- `src/Export/`：导出器、文件命名与路径
- `src/Diagnostics/`：独立日志、调试模式、运行统计

## 5. 线程模型建议

### 主线程

仅负责：

- 从补丁点提取必要字段
- 构造轻量事件对象
- 快速入队

### 后台线程

负责：

- 批量出队
- 聚合计数
- 生成导出快照
- 处理磁盘写入

### 同步原则

- 共享队列只通过同一个锁对象访问
- 快照导出前复制数据视图或短时间加锁
- 禁止在多个地方定义不同粒度锁，避免死锁和复杂竞争

## 6. 风险点

## 6.1 埋点选型风险

实际“真实需求”不一定能通过单一方法完全表达。若 `CreatePath` 只给出路径层面的起终点，而不能可靠标记出行目的，则需要补充更上游的 AI 决策埋点。

## 6.2 内存风险

如果不控制快照周期，长时间游玩可能导致稀疏矩阵持续增长。需要预留以下策略：

- 手动清空统计
- 自动滚动快照
- 仅保留当前周期统计

调试模式下还需额外关注原始记录增长问题，建议：

- 只在显式调试开关打开时启用原始记录保留
- 对原始记录保留数量设置上限或分段落盘策略

## 6.3 序列化兼容性风险

由于目标是 net35，不能默认使用较新的 JSON API。序列化方案应在实现前单独验证可用性与输出大小。

## 6.4 游戏升级与模组兼容风险

游戏版本、Harmony 版本以及其他 Mod 的补丁顺序都可能影响埋点稳定性。建议在补丁初始化阶段输出明确诊断信息。

## 7. 推荐落地顺序

1. 建立入口类与 Harmony 初始化
2. 用最小补丁验证候选埋点可触发
3. 建立 `ODEvent` 与网格映射函数
4. 补抓游客意图
5. 建立去重与真实意图/重试分类
6. 增加路径层对照埋点
7. 建立原始记录模型与压缩整数记录模型
8. 实现兼容 net35 的缓冲区
9. 实现固定网格顺序索引
10. 实现内存聚合器
11. 生成最小 JSON 快照
12. 补充独立日志与错误保护
